# Executor

Execution is sequential and result-oriented. `SafeExecutor` routes plan actions by mode:

- **READ ONLY / DRY RUN** — never mutate Logic. A valid action reports `dry_run`; an invalid one reports `not_executed` with the validator's message. DRY RUN is the UI default.
- **LIVE** — available only by the user's explicit mode choice plus a per-run confirmation. Only actions with `status == .valid` from `CommandValidator` are ever considered; each is routed to the first registered `LiveActionAdapter` whose `supports(action)` accepts it. An action no adapter supports keeps the honest refusal ("No verified live Logic adapter is installed for this action") without touching Logic.

## Adapter contract (`LiveActionAdapter`)

An adapter must locate its target from live AX evidence (never coordinates), prove its write mechanism before the first real write, re-read the control after every write, and return an `ExecutionResult` whose `before`/`after` are the re-read values — never the plan's numbers. A write that does not verify must be rolled back to the original position before the failure is reported.

## The verified channel-strip adapter (`LogicChannelStripAdapter`)

Covers exactly five actions: `set_volume`, `set_pan`, `set_mute`, `set_solo`, `set_send_level`.

- **Strip resolution** — the live Mixer areas are searched FIRST, with the scanner's own evidence and dedup (`StripResolutionMath`, a pure tested decision): "mixer"-described AXLayoutAreas of volume-fader strips, the area with the most strips being the real Mixer, smaller areas being inspector mirrors that contribute only names the Mixer does not show. A unique caption match resolves from the real Mixer; two same-named strips there are refused as ambiguous, and the captured AX path never breaks that tie. Only a caption no area shows falls back to the snapshot's captured AX path, walked and trusted only when the element it lands on still carries the strip's exact caption and a volume-fader slider — and every failure of an action resolved that way names the captured-path provenance and the open-the-Mixer-and-rescan recipe.
- **Mute / solo** — documented `AXPress` on the strip's own control captioned exactly `mute` / `solo`; the toggle counts only when the control re-reads as the target state. A control already at the target is not pressed.
- **Staleness gate** — when a volume/pan/send action carries the direction proof's `parameters.current`, the live reading must still match it (tolerance 0.05) before anything is written; a project that drifted since the analysis fails with "rescan and validate the plan again" instead of executing deltas nobody reasoned about. The gate fires before ANY write, the mechanism proof included — a refused action has provably not touched the control at all.
- **Write clamping and the driven, proven rollback** — the live Logic fader applies each AXValue write only as one bounded step toward the written value (a real Stereo Out run moved ≈0.1 dB per write), so no single write is ever trusted to land. Every slider action (`set_volume`, `set_pan`, `set_send_level`) runs through one write discipline (`CalibratedSliderWriter`): staleness gate, idempotent mechanism proof (read → set(the same value) → read — and when even that write moves the displayed value, the clamping fact is named, the control is driven back and the action refuses), then a drive whose every write is re-read and whose give-up is progress-based — a whole stagnation window of readings that set no new record toward the target — never a small fixed budget (a hard 1200-write cap remains as a loop guard). On ANY failure the control is DRIVEN back to its original position with the same clamped-write discipline (a single restoring write would strand a clamping control between two positions — exactly the −1.0 dB the first live run left behind), and the return is proven by re-reading the displayed value: the failure message states either the verified restoration or the EXACT value the control was left at. No refusal ends in a silent third state.
- **Volume** — calibration is mandatory because Logic's fader has been observed publishing raw units over AX (AXValue 173 while the level text reads 0.0 dB). The scale is decided from same-moment evidence (`FaderScale.detect`): AXValue equal to the displayed dB (tolerance 0.05) proves the dB scale; anything else is raw. On the dB scale the target is driven directly and verified against the displayed dB. On the raw scale no curve is guessed: `FaderServoMath` steps the fader with measured secant iterations bounded by the slider's own AXMinValue/AXMaxValue, tolerating the write clamping by progress, and the action succeeds only when the strip's displayed dB reads the target within 0.05. Any failure (no bounds, unresponsive display, stagnation, a bound-pinned fader) ends in the driven, re-read-proven rollback above.
- **Pan** — the pan facts and the validator's −64…+63 range come from this slider's own AXValue, so the write is on the fact scale by construction; it runs through the same discipline (staleness, idempotent proof, clamped drive, driven rollback) with the AXValue itself as the verified reading.
- **Send level** — the send is located by the same structural evidence the normalizer publishes the fact from: the destination-captioned AXGroup holding a "bypass" checkbox (matched to the plan's `target.sendDestination`, unique or refused), with the "send knob" AXSlider directly after it. The write runs on the scale the knob itself proves live. When the knob's `AXValueDescription` displays dB, the write is the same calibrated dB procedure as the volume fader (shared code path, verified against that description). When no dB is displayed anywhere, the only proven scale is the knob's bare AXValue (the exact scale the validator's range came from — the knob's own AXMinValue…AXMaxValue): the same discipline with the AXValue as the verified reading, `parameters.current` gated in raw units. The validator has already refused `set_send_level` for any send whose scale no scan proved, so the adapter never receives a target on a scale nobody measured. Send pan has no adapter and never will while Logic exposes no send pan control: `set_send_pan` validates as unsupported.
- **One reading, two readers** — the adapter's verification reading and the scanner's Volume fact come from the same evidence with the same grammar: the strip's own `volume fader level` text, title first, then value (`SnapshotNormalizer.makeChannelFacts` and the adapter's display closure parse identically). They also resolve the strip from the same evidence: the adapter searches the live Mixer areas first with the scanner's own largest-area/mirror rule, so with an open Mixer both readers land on the same element by construction — the captured AX path can no longer steer the adapter onto an inspector mirror (same caption, same fader, potentially stale AXValue) while the scanner reads the real Mixer; that mirror divergence was observed on a real run (adapter −1.0 dB, fresh scan 0.0 dB) and is what the precedence exists to remove. The divergence class survives only in the fallback, when no live Mixer area shows the strip's caption (Mixer window closed or hidden): the adapter then walks the captured AX path, whose element Logic may not be redrawing, and names that provenance in every failure. When that happens, open the Mixer window (X) so Logic renders the strips and rescan before trusting either number.

## Queue semantics

Actions run strictly in plan order. A `failed` adapter execution halts everything after it — later actions were often reasoned against the state the failed one should have produced — and every halted action reports `not_executed` naming the failure. After a LIVE queue the app runs a fresh read-only `fullScan`, normalizes it and shows `DiffEngine.compare` (changed / unchanged / errors, including mute/solo changes) next to the per-action results.

Actions outside the five (plug-ins, send pan, routing) still fail safely: no adapter exists for them and none is guessed.

## Verification cycle (closed before/after loop)

The loop closes after the plan is applied — automatically after a LIVE queue, or by the Review screen's "Verify Applied Plan" button for a plan the user applied by hand. One fresh read-only scan then: (1) diffs the tracks against the snapshot the plan was validated with; (2) checks every `valid` action's absolute target against the re-read known fact (`PlanVerifier`, tolerance 0.05 — the validator's own) with three honest outcomes — `matched`, `mismatched` (both values shown), `unverifiable` (a non-known fresh fact is stated as such and never guessed into a result); (3) freezes the current files' measurements as the pre-apply baseline (`MetricsBaselineEntry`) — control moves change the audio only after a new export/bounce, so the files on disk at verification time still carry the state the plan reasoned from; and (4) ADOPTS the fresh snapshot as the current analysis.

After that the user can re-export the tracks and re-bounce the mix from the same card; `MetricsComparison` joins the frozen baseline with the newly measured files by identity (rows exist only where both sides were really measured — the metrics cache keys by file identity, so an unchanged file keeps identical numbers and is flagged "unchanged file", never presented as the plan's sonic effect). The next generated AI package is then the post-apply second round: schema ≥ 2.27 marks it `Post-apply snapshot: yes` and carries the verification lines, the track diff and the before/after metrics in a `Post-apply verification` section, so the model assesses what the applied plan actually achieved and proposes the next circle from the fresh facts alone.
