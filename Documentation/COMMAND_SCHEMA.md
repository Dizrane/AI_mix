# Command schema

`MixPlan` is JSON: `version`, `status`, and `actions`. Every action has `id`, `target`, `action`, `parameters`, `reason`.

The complete declared vocabulary is in `MixAction`; the current safe executor supports validation of volume, pan, mute, solo, send level, send pan, plugin bypass, and plugin parameters. Unsupported actions are explicitly rejected. Every implemented action requires a typed `parameters.value` holding the absolute target setting (never a relative change): numeric for `set_volume` / `set_pan` / `set_plugin_parameter`, boolean for `set_mute` / `set_solo` / `set_plugin_bypass`; a missing or mistyped value is invalid. `set_volume` must sit inside Logic's fader range −96…+6 dB and `set_pan` inside −64…+63 (`CommandValidator.volumeRangeDB` / `panRange`); out-of-range values are invalid. `set_volume` and `set_pan` additionally require the direction proof: `parameters.current` restating the track's current known channel fact and `parameters.delta` = target − current, signed. The validator checks the arithmetic (current + delta = value, tolerance 0.05) and checks `current` against the known fact when one exists; a track without a known fact is not guessed — the arithmetic alone still pins the stated direction to the value. `set_send_level` targets a send with `target.sendDestination` — the send's Destination fact copied exactly (a track with two sends to one destination is rejected as ambiguous; a missing send is `requires_probe`). It is executable only for a send whose Level is a `known` fact on a proven scale (`SendFacts.levelScale`): the value, `parameters.current` (the send's Level fact) and `parameters.delta` are all on that scale — dB when the knob's own `AXValueDescription` displays dB, the knob's raw units otherwise — and the value must sit inside the send's proven range (`SendFacts.levelRange`, the knob's own bounds) when one is published. A send whose scale is unproven keeps `set_send_level` **unsupported** — exactly the status the whole action had before send facts existed. `set_send_pan` always validates as unsupported: Logic exposes no send pan control over Accessibility, so no scan can ever prove a scale for it. Action ids must be unique within the plan and `reason` must be non-empty — the validated plan is the user's instruction sheet (only the verified channel-strip actions — volume, pan, mute, solo and proven send levels — have a live adapter, everything else stays manual), so each action carries its own justification. `reason` is the one human-readable field inside the JSON and is written in the user's language (the Review screen shows it to the user under each action; the validator checks only non-emptiness); keys, action names, ids, track identifiers and values are machine-matched and stay exactly as the facts state them. Plugin parameter changes additionally require an observed plugin, observed parameter, and reported range when present. The Review screen accepts the plan as a bare JSON object or inside a Markdown code fence (```json … ```), including a fence pasted with surrounding prose, and displays each action's move as "current → target (Δ signed)" with its reason.

Example:

```json
{"version":"1.0","status":"ready","actions":[{"id":"volume_1","target":{"trackID":"aux"},"action":"set_volume","parameters":{"value":-3.0,"current":-1.0,"delta":-2.0},"reason":"Volume is known -1 dB; the target -3 dB moves the track down 2 dB because its measured RMS sits above the mix bed."}]}
```
