# LLM contract

The package reaches a model in three deliveries. Two are manual: the user hands the stage-4 AI Package to any external LLM themselves — the saved full package (with `logic_snapshot.json`, the track WAVs and the bounced Stereo Out mix) or the Copy-for-AI Markdown alone — and pastes the answer back into the Review screen. The full-package instructions require the model to listen to the tracks and separately to the sum: overall balance, masking, stereo image and master-chain results are supported by the mix bounce, never inferred from isolated assets. Each delivery is self-sufficient, and all state the same MIXED DELIVERY rule for the case where the pasted Markdown and the ZIP arrive together: the full package is the delivery that matches reality, so its rules take priority over the text-only variants' delivery claims — the delivery variants differ only in their preambles and response contracts; every fact in them is identical.

The contract the document teaches: the model is the decision maker and works only from supplied facts (states other than `known` are not evidence and are never guessed). The workflow is human-in-the-loop in two strictly separated replies — the first delivers ANALYSIS / INTERPRETATION / ISSUES / QUESTIONS and no machine-readable deliverable, opening ANALYSIS with one explicit line declaring the audio mode (listened to the WAVs, or working from the measurements because listening is impossible or the audio was not delivered); only after the user's confirmation does the second deliver the deliverable — `MIX PLAN` (exactly one JSON block conforming to the `MixPlan` schema, see `COMMAND_SCHEMA.md`) plus `MANUAL STEPS` on the manual paths, or exactly one fenced json MixGraph block on the API path. Prose — including each Mix Plan action's `reason` inside the JSON — is written in the user's language; the rest of the JSON stays exactly as the facts state it. A pre-delivery checklist in the package mirrors the app's own validator. The embedded JSON example is built only from the snapshot's (or export's) own known facts; without them it uses an empty example instead of fabricating a target.

The third delivery is the API path: the Assistant stage sends the `.apiDelivery` variant of the same document into a Capy thread over the Capy API and runs the whole dialog itself — polling to a settled thread status, relaying the user's stage-5 confirmation (or one fixed accept-all-defaults line), and on rejection one fixed message naming the dry-validation errors. Its preamble states that the text was sent programmatically, that no files are attached, and that the final deliverable is a MixGraph, not a Mix Plan: after confirmation the model replies with exactly one fenced json code block, the application extracts the LAST such block of the transcript, decodes it against `MixGraph` 1.0 and dry-validates it (`MixGraphDryCheck`: file names against the really exported WAVs, send buses, pan ranges, insert identities against the installed Audio Unit catalogue — the same checks a manual paste on the Render screen gets). A valid graph lands in the Render screen's editor; rendering runs offline in `MixEngine` and starts only on the explicit Render press. Unlike the Mix Plan paths, plug-in inserts are real machine actions here: the MixGraph names installed effects by their exact FourCC component identifiers from the Available Plugins catalogue (published with every entry, in every delivery), and the engine sets their parameters through `AUParameterTree` with read-back. There is no other in-app transport: without a Capy key the Assistant stage only points at the manual paths, and the app remains fully usable through them.
